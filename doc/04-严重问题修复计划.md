# 严重问题修复计划

## 背景

当前路线图中的功能大多已标记完成，但手动验收和代码审查发现，部分功能仍存在数据安全、内容安全和运行时一致性风险。本计划优先收敛这些问题，暂停继续扩展非关键功能。

本计划完成前，不将“现有单元测试全部通过”视为可发布依据。每个严重问题都必须先建立可复现测试，再实施修复。

## 总体原则

1. 优先保护事实数据，再处理页面体验。
2. 所有数据丢失和权限问题必须有失败路径测试。
3. 不通过前端隐藏按钮代替后端权限控制。
4. 评论、搜索摘要等用户可控内容不得未经消毒直接使用 `v-html`。
5. `doc/00-需求手册.md`、`doc/01-数据库表设计.md`、`doc/02-后端API设计.md` 是冻结契约。新增 API 或改变端点语义前，必须先获得人工批准并更新契约文档。
6. Playwright 放在严重问题基本收敛后引入，作为真实浏览器验收工具，而不是用来掩盖应用逻辑缺陷。

### P0-1：修复编辑页正文丢失风险

问题：

- `frontend/src/views/EditView.vue` 在没有草稿时将编辑器正文初始化为空字符串。
- 后端已有 `docservice.HeadContent`，但当前没有前端可调用的 HEAD 源码接口。
- 用户打开已有文档后直接保存，可能将原正文覆盖为空。

实施步骤：

1. 核对 `doc/02-后端API设计.md` 是否已有可读取 HEAD 源码的端点。
2. 若没有，先提交 API 契约变更申请，确定新增端点的路径、权限和响应结构。
3. 在无草稿时加载 HEAD 源码，在有草稿时加载草稿。
4. 确认打开文档不会自动生成空草稿或空版本。
5. 保留文档 ID 切换时的请求序列隔离。

验收测试：

- 已有正文、无草稿时，编辑器显示 HEAD 正文。
- 不修改直接保存，正文内容不变。
- 有草稿时，编辑器优先显示草稿。
- 不存在 HEAD 版本时，编辑器显示空内容。
- 文档不存在或无权限时显示明确错误，不显示空白编辑器。

### P0-2：修复评论持久型 XSS

问题：

- `frontend/src/components/doc/CommentsPanel.vue` 使用 `v-html="c.content"`。
- 后端保存评论原文，恶意评论可能在其他用户查看时执行脚本。

实施步骤：

1. 短期将评论按纯文本渲染，禁止原始评论进入 `v-html`。
2. 如果需求必须支持 Markdown，设计统一的安全 Markdown 渲染管线。
3. 对 HTML、script、事件属性、javascript URI 等攻击向量增加测试。
4. 审查搜索结果标题和 snippet 的 `v-html`，确认其来源和消毒边界。

验收测试：

- 评论中的 `<script>`、`onerror`、`javascript:` 不执行。
- 评论原文可以正常展示或安全渲染。
- comments disabled 门闩行为不变。
- 搜索结果中的恶意标题和摘要不执行。

### P1-1：修复自动保存空内容和提交一致性

问题：

- `useAutosave` 使用字符串真假判断待保存内容，空字符串不会保存。
- 编辑页标题防抖 PATCH 可能先于正文 commit 成功，正文冲突时标题仍然被修改。

实施步骤：

1. 在自动保存状态机中增加独立的 pending 标志，区分“无待保存内容”和“待保存空字符串”。
2. 清空正文后验证草稿能够保存和恢复。
3. 重新设计标题保存与正文 commit 的顺序。
4. 确保 409 冲突时标题、正文、HEAD 和草稿符合契约中的零污染语义。
5. 验证文档切换和组件卸载时不会继续写入旧文档。

验收测试：

- 清空正文后自动保存请求包含 `content: ""`。
- 刷新后清空状态保持。
- 并发冲突时不产生非预期标题修改。
- A 文档的延迟自动保存不会写入 B 文档。
- 离开确认后保存目标和当前文档一致。

### P1-2：统一认证初始化

问题：

- Router 守卫和 `App.vue` 分别请求 `/v1/users/me`。
- 两次请求的先后和失败结果可能导致权限状态被错误清空。

实施步骤：

1. 建立唯一 auth store 或共享初始化 Promise。
2. Router 守卫等待统一认证初始化结果。
3. App 只消费认证状态，不再重复初始化。
4. 区分未登录、认证请求失败和认证初始化中三种状态。
5. 验证登录、登出和 session 过期时权限能够及时清理。

验收测试：

- 有效 session 下并发加载页面不会丢失权限。
- `/users/me` 只执行一次初始化请求。
- 未登录访问受保护页面保留原始目标。
- session 过期后受保护路由回到登录页。
- 网络失败不会被错误地当成永久未登录。

### P1-3：统一页面错误边界

问题：

- Search、Trash、Tokens、Comments 等页面对 API 失败处理不一致。
- 部分页面可能显示空内容、未处理 Promise 或直接暴露错误字符串。

实施步骤：

1. 统一使用 `ApiError.status`、`detail` 和 `fields`。
2. 页面统一建模 loading、ready、unauthorized、forbidden、notFound、networkError、serverError 状态。
3. 为页面提供重试或返回入口。
4. 禁止直接渲染 `String(error)` 作为用户文案。

验收测试：

- 401 进入登录流程并保留目标。
- 403 显示无权限页面。
- 404 显示资源不存在页面。
- 网络错误显示重试入口。
- 所有错误路径没有白屏和未处理 Promise。

### P1-4：完成深链接和部署闭环

问题：

- 前端使用 `createWebHistory()`。
- 生产静态服务的 SPA fallback 尚未验证。
- OIDC callback、前端地址和 Cookie 主机名必须保持一致。

实施步骤：

1. 生产环境由 Nginx 提供前端静态资源，配置见 `deploy/nginx.conf`。
2. 为非 API GET 请求配置 `index.html` fallback，同时保留 `/v1/` 和 `/healthz` 反向代理。
3. 统一 `base_path`、前端公共地址、OIDC callback 和 session cookie 配置。
4. 测试直接访问和刷新 `/docs/id`、`/docs/id/edit`、`/search`、`/admin`。

验收测试：

- 所有深链接直接打开和刷新均返回前端页面。
- OIDC 登录成功和失败均回到正确的前端地址。
- 使用 `localhost` 或 `127.0.0.1` 时不会混用主机名。
- HTTPS 生产环境使用 `secure_cookies: true`。

## Playwright 引入条件

满足以下条件后，再单独引入 Playwright：

1. P0-1 和 P0-2 已修复并有自动化测试。
2. 自动保存、并发冲突和认证初始化的单元/组件测试通过。
3. 前端不再有未捕获运行时异常导致白屏。
4. OIDC 登录、登出和前端回跳手动验证稳定。
5. 生产深链接服务方案已经确定。

Playwright 第一批只覆盖关键真实链路：

1. 未登录访问受保护深链接。
2. OIDC 登录后回到原始页面。
3. 查看文档 A 切换到 B。
4. 编辑文档、自动保存、提交和返回。
5. 401、403、404 和刷新深链接。
